The Problem

EV loan underwriting at Vidyuttech runs through a manual review process — an analyst reads each applicant's documents, income proofs and risk signals, and makes an approve / reject / refer call. It's accurate, but it doesn't scale, and a good chunk of applications are genuinely straightforward: the decision is obvious once the right data is in front of a reviewer.

The instinct is to point an LLM at the case file and let it decide. I pushed back on that framing early. An underwriting agent that's wrong 5% of the time isn't a productivity tool — it's a new source of bad loans, and a false approval is categorically worse than a false rejection. The real problem isn't "can an LLM do this," it's "how would we ever know if it's safe to trust."

"The interesting engineering problem here was never the model. It was building an evaluation process rigorous enough that a good benchmark score actually means something."

Why Evaluation Comes Before the Model

Most LLM pilots I've seen fail quietly: the model looks great on a handful of examples the team already knows the answer to, gets a green light, and then underperforms once real, messy cases hit it. I wanted the evaluation itself to be the hard part — designed so a good score is actually earned.

That meant treating the benchmark like a controlled experiment, not a demo:

  • The agent never sees the ground-truth decision for a case until after it commits to an answer.
  • Case packets are compiled blind — no field in the packet reveals which way the original human underwriter went.
  • Every model decision is cryptographically hash-frozen the moment it's produced, before comparison to the true label, so there's no possibility of quietly re-running a case that came back wrong.
  • Comparison against ground truth happens on an air-gapped process, verified independently of the agent's own environment.

The goal was simple: make it structurally impossible for the evaluation to flatter the model, even by accident.

Calibration Discipline

Once the agent's decisions diverge from a human underwriter's, the tempting move is to patch the prompt or policy logic for that one case and move on. I set a harder rule instead: no calibration change to policy behaviour is accepted on the strength of a single case. Every proposed change needs independent corroboration from at least three separate cases before it's adopted.

That single rule filters out a lot of noise — a lot of "the model got this one wrong" turns out to be one ambiguous case, not a real pattern, and treating it as a pattern is how you quietly introduce a new failure mode while fixing an old one.

Finding the Bugs That Weren't the Model's Fault

Before I could trust any accuracy number, I had to trust the data feeding the model — and it wasn't clean. Direct SQL investigation of the upstream pipeline surfaced several defects that were silently corrupting case inputs:

1
Join fan-out

A one-to-many join was silently duplicating rows, causing fields from unrelated records to bleed into a case packet that should have been single-applicant.

2
Deduplication logic errors

A dedup step was keeping the wrong record in a handful of edge cases, feeding the model stale or superseded values.

3
Independent verification

I added PMT/FOIR recomputation as an arithmetic sanity check, repeated-run stability testing to catch non-deterministic output, and source-document cross-checks — so fabricated or duplicated data gets caught before it ever reaches a decision.

None of these would have shown up as a model problem. They'd have shown up as an unexplained accuracy ceiling, and the wrong fix for that is tuning the prompt harder.

Current Status

Lumen is in calibration and benchmark evaluation now — not deployed, and not making live underwriting decisions. The >90% accuracy and 60%+ coverage figures above are the design targets that would justify shipping it, not results I'm claiming today. The next gate is a blind holdout run under the same leakage-proof conditions described above; only that clears the agent for a limited pilot.

What I'd Want in Place Before Go-Live

Beyond the accuracy bar, I'd want a monitored shadow period — the agent runs alongside human underwriters without its decisions taking effect, so drift shows up before it's live. And I'd want the false-approval constraint checked continuously in production, not just at the benchmark gate, since a policy or data distribution shift months later is exactly the kind of thing a one-time evaluation can't catch.
